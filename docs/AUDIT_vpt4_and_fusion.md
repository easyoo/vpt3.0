# 审计报告：vpt4.0 指标是否虚高 + mapping⊕MemoryBank 融合步骤是否有误

结论先说：**没有发现导致指标虚高的代码错误或口径失误**。所有关键数字都能被**独立路径复现**（逐位一致）。
但有几处**必须如实披露的口径假设**（不是 bug，而是"这个数字在什么前提下成立"），列在 §4。

---

## 1. 复现性核验（最有力的反证：数字能否用另一条路算出来）

| 核验项 | 做法 | 结果 |
|---|---|---|
| 验收指标（mapping-only） | 用 `eval_offline.py`（验收路径）与 `fuse_eval.py --rule improved_only`（缓存路径）分别算 15 类 | **15 类 × 7 指标逐类差异 = 0.0000** ✔ |
| bank 分支异常图 | 从零**重建** MemoryBank（4 shot×22 增强，seed=1）再算图，与缓存逐图比较 | 最大差异 **0.000000**；bank-only 指标完全一致 ✔ |
| bank-only 指标 | 与项目此前记录的"仅 bank"列比对（§21.4） | 0.9803/0.9898/0.9721/0.9666/0.6368/0.6392/0.9327 **逐位一致** ✔ |
| 基线可复现 | 用 `code_norm` 独立重跑基线权重（transistor / pill） | 0.7462/…/0.6764 与 0.5987 与记录**一致** ✔ |
| 代码副本是否给本方案"额外优势" | **regD2 对照**：用我们的代码、但把机制全关（`init=1e-6, w_div=0, global_proto=0, metric_head=0`）训练 leather/pill/zipper，与记录的基线比 | 0.4409(基线0.4301) / 0.5707(0.5986) / 0.7096(0.6963) → **偏差 ±0.03 以内**，无系统性优势 ✔ |

## 2. 有没有"偷看测试集"（泄漏）——逐项排查

| 可能的泄漏点 | 检查方式 | 结果 |
|---|---|---|
| 辅助异常集含测试图 | 对 15 类合成图与 MVTec test/train 图做 **md5 全量比对** | 2100 张合成图，与 test **0 重复**、与 train 0 重复 ✔ |
| 合成异常的底图来源 | 查 AnoStyler 配置：`normal_image: .../normal_imgs/mvtec/<cls>/*.png` | 逐类抽样：底图 **4/4 与 `train/good` 哈希相同、0 与 test 相同** ✔ |

| 逐类超参调优 | 读训练清单 `manifest_train_m4m6r3_15.txt` | 15 类的 `EXTRA` 参数**完全相同**，无逐类调参 ✔ |

## 3. 融合步骤（0.3·z(mapping)+0.7·z(bank)）逐环检查

1. **逐图对齐**：三种缓存（mapping / bank / GT）形状一致 `[N,1,392,392]`；
   用 `MVTecDataset(test)` **重建标签序列**与缓存 `meta['labels']` 对比 → **完全一致**（transistor 100 张、40 张有缺陷）；GT 的有无缺陷与数据集逐图一致 ✔
2. **归一化位置**：`z_cls(x)=(x-mean)/std`，mean/std 取**整类全部像素**（不是单图范围）✔ ——与"类别内归一化"要求一致；
   注意 z 是**单调仿射变换**，它**不会**改善任何单分支的排序指标（AUROC/AUPRO 不变），只影响两支融合的相对尺度 ✔
3. **融合顺序**：先融合、后**一次**高斯平滑（`gk(fused)`），不存在"两支各自平滑再融合"或重复平滑 ✔
4. **分辨率一致**：392 口径（`resize_mask=None`），mapping/bank/GT 都在 392 上；与基线所用协议相同 ✔
5. **图像级分数**：`top-1%` 均值（392²→1536 像素），与官方/基线口径一致 ✔
6. **指标调用**：`ader_evaluator(pr_px, pr_sp, gt_px, gt_sp)` 的参数顺序与训练脚本一致（官方 adeval）✔
7. **权重不是挑出来的**：0.3 是用户指定；扫描 0.2/0.3/0.4/0.5 显示 **0.3≈0.4 并列最优**，0.2/0.5 更差 → 没有"取最好看的权重"的嫌疑 ✔

## 4. 必须如实披露的口径假设（不是错误，但要写清楚）

1. **打分含"自参照"**：mapping 的可学习原型来自**被测图自身**（transductive，不使用标签）。
   这是 vpt3.0 既定设计，**基线与本方案完全一致**；它带来的性能不能归因于"我们引入了测试信息"。
2. **融合的类内 z 用了测试集统计量**：这是 vpt2.0/vpt3.0 的既定融合协议，也是用户明确要求的口径；
   由于 z 单调，它不影响单分支指标，只决定两支相对权重。若要最严格（归纳式）口径，需改用训练集统计量，届时两支权重会变、数字需重算。
3. **基准即测试集**：MVTec 的 test 就是benchmark。本方案的机制/超参是在**同一测试集**上筛选的（5 类→15 类），
   因此这些数字**不是"留出集"结果**；正式论文口径应另设验证集选型、只在测试集上报最终一次。
4. **训练期会打印测试指标**：训练脚本每 5 轮在测试集上算一次指标用于监控（无梯度、不参与选型）。
5. **两支共享"正常参照"思想**：mapping 打分里已含"原始特征库图"（train/good patch 库），
   MemoryBank 是另一套（dinov2-base 中层特征 + faiss）。二者相关但不相同；融合的 1+1>2 属于**信息互补**，不是重复计数。

## 5. 顺带发现并已修的小问题（都不影响上述结论）

1. **统计脚本取数**：`compare_vpt4_7m.read_eval` 原先取日志**第一条**匹配行；重评后同一 tag 有多行 → 已改为取**最后一条**（否则会误用旧权重结果）。
2. **混版运行**：清单 `code_md5` 显示 15 类里有 3 类早于"初始化算子修复" → 已用同版代码重训重评，最终 15/15 同哈希。
3. **命名易混淆**：`.maps_audit/<cls>_improved.map` 是**旧（control 权重）**的 mapping 图，
   `.maps_audit/<cls>_improved_m4m6r3.map` 才是本方案的；两者都在盘上，后续引用务必看后缀。

## 6. 一句话总结

* **vpt4.0 的指标**：两条独立评估路径逐位一致、无标签泄漏、无逐类调参、无选轮，"虚高"没有证据支持；
* **融合步骤**：逐图对齐、类内 z、单次平滑、官方指标，权重 0.3 为用户指定且与 0.4 并列最优，**未发现导致虚高的错误**；
* 真正需要标注的是**口径假设**（自参照打分、类内 z、benchmark 即测试集），它们对基线与本方案**一视同仁**。
