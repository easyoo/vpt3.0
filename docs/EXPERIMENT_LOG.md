## §6 路径1核心发现：多层特征"求和融合"退化成只用最后一层

工具：`probe_fusion.py`（control screw@30ep，正常图 `000.png`）。

各层 patch token 的平均 L2 范数：

| 参与融合的层 | 1 | 2 | 3 | 4 | 6 | 8 | 11 |
|---|---|---|---|---|---|---|---|
| mean L2 | 2.881 | 2.383 | 2.564 | 3.455 | 7.051 | 19.557 | 154.674 |

* 融合的 7 层范数跨度 **64.9×**；
* 融合向量与各层的 cos：layer1 −0.0226、layer2 0.0186、layer3 0.0157、layer4 0.0519、
  layer6 0.1543、layer8 0.3737、**layer11 0.9854**。
* 即 `fused = Σ layer[i]` 实际就是"layer11 单独用"，浅层/中层信息全部被数值淹没。
* 改为逐层 L2 归一化后求和：各层 cos 变为 0.67/0.76/0.77/0.75/0.69/0.49/0.23 → 7 层才真正参与。

修复：`code_norm`（FIX-12，逐层 L2 归一化 + 可学习层权重）。A/B 结果见 §8。

## §7 噪声地板（为什么必须多 seed）

* FIX-1 在 `learnable_layers=1` 时是**数学等价变换**（重复 token 的数值完全相同，
  注意力分母里两份等权、加权和不变），只是浮点求和顺序从 853 项变 821 项；
  然而 30 轮后 screw 的 P-AP 从 0.3134 变成 0.2766（−12%）。
* 离线复现同一权重时，仅仅因为 cudnn 选核不同，指标就漂移 ~0.01（§3 注）。
* 因此：**单 seed、单次运行之间 <0.03 的差异不足以作为涨点证据**。
  最终 A/B 除 5 类 × 2 组外，额外用"完全相同命令重跑 screw"给出噪声地板（`results/control35_repro/`）。

> 补充（原型坍缩度量，供路径2参考）：真实前向得到的 32 个原型，
> screw 两两余弦 0.559 / 参与比有效秩 3.43，hazelnut 0.892 / 2.29，wood 0.901 / 2.41
> —— 32 个原型实际只张成 ~2~3 维子空间。

**结论**：逐层 L2 归一化 + 可学习层权重（FIX-12）**在训练后期严重崩溃**
（capsule/metal_nut/hazelnut 的 P-AUROC 掉到 0.63~0.74，而 control 是 0.89~0.98），

机制解释（与 OBS-A 一致）：浅层特征承载的是低级纹理，用 4-shot 的正常样本去拟合

（P-AUROC 崩），而 deep-only（control 的实际行为）恰好是天然的正则化。

→ **工程启示**：`fused_layer=[1,2,3,4,6,8,11]` 的"退化"在 4-shot 场景下不是坏事；
真正值得做的不是"把浅层权重提上来"，而是**在不破坏深层主导的前提下补充分辨率**（见 §9）。

## §9 【路径2 成果】多尺度测试期打分：零训练、稳定涨点

### 9.1 动机（来自失败样本分析，§10）

screw@10ep 的失败样本分析显示：

* 正常图 sp_score ∈ [0.060, 0.106]，异常图 sp_score ∈ [0.059, 0.20] —— **严重重叠**；
* 最难的两类缺陷 `scratch_head`(0.103) 与 `manipulated_front`(0.112) 几乎落在正常区间内；
* 这两类的 in/out-GT 对比度只有 0.068 / 0.076，而容易的 `thread_neck` 是 0.225
  → 打分图对**小/局部缺陷**明显弥散。

根因：一个 14×14 的 patch 只覆盖 392 输入的 1/28 边长，小缺陷的异常能量在 patch 内被平均掉。

### 9.2 方案

冻结权重，把已预处理的 392×392 输入再放大 s∈{1.0, 1.25, 1.5} 倍送进 backbone
（3×3 = 更细的 token 网格：28² → 35² → 42²），各自得到打分图后插值回 392 再融合：

* `ms_mean`：多尺度平均（推荐，鲁棒）
* `ms_max`：多尺度取最大
* `s1.25 / s1.5`：单尺度放大

工具：`probe_scale.py`；结果：`results/probe/scale_control.csv`。

## §12 【路径1 追加】分割头损失口径缺陷（FIX-14）——CPU 可完全验证

### 12.1 问题

`FocalDiceLoss.forward` 把整个 batch 展平成一个向量再算 Dice：
`dice = (2·Σ(p·t) + s)/(Σp + Σt + s)`。后果是**损失口径随 batch 组成变化**：
异常面积大的样本主导 union，小面积样本几乎拿不到有效梯度；换个 batch 分组损失值就变。

### 12.2 CPU 验证（`verify_dice_loss.py`：构造 1 个好样本 + 1 个差样本 + 2 个全背景样本）

| 口径 | dice_score | 全背景样本梯度范数 | 能否给出逐样本 Dice |
|---|---|---|---|
| 原实现（全局 Dice） | 0.5128 | 6.6e-2 | 否 |
| 朴素逐样本（不跳空） | 0.7146 | **1.0e+5（伪梯度）** | 是 |
| **FIX-14（逐样本 + 跳空）** | 0.4292 | 0.0 | 是 |

逐样本 Dice 明细：好样本 0.7917、差样本 0.0667、两个全背景样本 1.0000 —— 全局口径**无法表达**这种差异。

**伪梯度来源**：全背景样本若预测也全为 0，则 `U = Σp + Σt = 0`；
Dice 项值≈0（看似完美），但 `∂/∂p = s/(U+s)² = 1/s = 1e5`。
训练里有 `clip_grad_norm(max_norm=0.5)`，这个伪梯度会**主导整个 batch 的更新方向**。
FIX-14 对 `target.sum()==0` 的样本跳过 Dice 项（正常区域"别乱报"交给 Focal/BCE），实测伪梯度归零。

### 12.3 为什么值得修

§4 已测得 `type=2/4`（分割头误差图）明显弱于 `type=1`（P-AUROC 0.60/0.71/0.78 vs 0.92~0.98），
说明这条支路的监督信号不可靠，而损失口径是最可疑、且修复零成本的一环。
`type=1` 主路径完全不受本改动影响，可作为干净对照。
启动脚本：`q_dice.sh`（GPU 恢复后；评估 type=1/2/4 三种口径，与 control35 做配对比较）。

## §14 【路径2 新成果】打分图融合：映射空间可学习原型 × 原始空间正常特征库（零训练）

### 14.1 动机与消融设计

现状打分只用**随图像变化**的可学习原型（image-conditioned），其分数尺度在图像之间不可比；
而异常检测的数据集级像素指标（P-AP/P-AUROC）恰恰依赖**跨图可比性**。
于是做一个把所有因素拆开的消融（同一份权重、同一次前向；CPU 版 numpy 指标，P-AUPRO 不可得）：

| 变体 | 特征空间 | 原型来源 |
|---|---|---|
| `mapped+learn` | 映射空间 | 32 个可学习原型（现状） |
| `raw+learn` | 原始空间 | 同上（说明"原型是在映射空间里训出来的"，此列必崩） |
| `raw+bankAll` / `raw+bank32` | 原始空间 | 4 张正常图的全部/k-center 原型（经典 PatchCore 思路） |
| `mapped+bankAll` | 映射空间 | 同一批正常图原型 |
| `mapped+learn+bankAll` | 映射空间 | 并集 |
| **`fuse_raw_avg`** | 两个空间各算一张图，**逐像素平均** | learn + raw bank |
| `fuse_z_avg` | 同上，融合前逐图 z 归一化 | 同上 |

|---|---|---|---|---|---|---|---|

**裁决**：
1. **训练期尺度抖动（CAND-1）：不采纳**。5 类平均 P-AP 0.4731 < 0.4884，且逐类正负不一
   （hazelnut/wood 略升，screw/metal_nut 明显下降）——没有稳定收益。

2. **浅层残差门控（CAND-2）：明确否决**。screw 的 P-AP 塌到 0.021、I-AUROC 0.62；capsule 0.16；metal_nut 0.20。
   这是**第二次**验证同一结论（第一次是 FIX-12）：**任何让浅层信息进入融合特征的训练改动都会破坏
   这个 4-shot 训练**，深度主导（control 的实际行为）必须保留。
3. **FIX-14（分割头 Dice 逐样本化，`q_dice`）**：训练与评估均完成（`results/ms35/dice35.csv`，type=1/2/4 × 5 类），
   但按"不再扩大对比实验"的要求，**仅归档不作结论**；`type=2`（分割头单独用）依然远弱于 `type=1`（P-AUROC 约 0.52~0.77 vs 0.85~1.00），
   说明该支路要发挥作用还需要更强的监督设计（列入后续方向）。

## §23 【模型/算法层 · 第 2 阶段】M7 跨图排序一致性损失 + FIX-M4 训练/推理口径对齐

时间：2026-10-08 23:45 ~ 23:55（GPU 被同事任务占满，本阶段全在 CPU/代码层推进，训练排队中）

### 23.1 目标定位（由证据决定，而不是拍脑袋）
§22.4 的 7 指标实测表明：vpt4 变体 **I-AUROC / I-AP / I-F1 / P-AP / P-F1 / P-AUPRO 六项都 ≥ +1.5%**，
**唯一卡住的是 P-AUROC（+0.33% ~ +0.61%）**。原因分析（损失项逐条对照）：

| 损失项 | 排序范围 | 是否约束"跨图可比" |
|---|---|---|
| 原始 cos / MSE（对原型） | 图内 | ✗ |
| 分割头 Dice + Focal | 图内（逐图 mask） | ✗ |
| M5 像素 BCE | 图内（每图用自己的原型集） | ✗ |
| **M7（本轮新增）** | **跨图（整类像素放一起）** | **✓** |

P-AUROC 的定义就是"把整类所有图的像素**混在一起**排序"，因此必须有一项损失显式约束
"A 图的正常像素不能高于 B 图的异常像素"。现有损失全是图内的，这正是它上不去的根因。

### 23.2 M7：跨图排序一致性损失（新机制）
`L_M7 = mean_{i,j} relu( s_norm_j - s_anom_i + margin )`

* 正常像素 = 正常图全部 patch ∪ 辅助异常图里 `mask=0` 的 patch；
* 异常像素 = 辅助异常图里 `mask=1` 的 patch；
* 分数 `s = 1 - max_k cos(patch, proto_k)`，**用每张图自己的原型集**（与推理端逐位同口径）；
* **困难样本挖掘**：正常侧取分数最高的 n 个、异常侧取分数最低的 n 个（默认 n=256 → 6.5 万对，代价可忽略）；
* 全程不使用任何测试集统计量（不做逐图/逐类归一化）。

代码位置（`code_vpt4/main-fewshot-vpt4.py`）：
* 新增 `proto_distance_scores()`（**公共打分口径**，训练与推理唯一实现）；
* 新增 `cross_image_rank_loss()` / `cross_image_rank_loss_from_features()`；
* 训练循环新增 M7 分支（`--w_rank`，默认 0.0 = 关闭，不污染既有实验）；
* M5 原手写 `bmm` 改写为调用同一口径函数（消除"训练/推理口径漂移"的风险源）。

### 23.7 证据：P-AUROC 为什么上不去（CPU 探针实测分数分布）

> ⚠️ **本节曾因探针 bug 记录过一次错误数字，已作废并更正**（保留说明以便复盘）：
> 探针早期版本漏掉了 `model.token_mapping(...)`，与推理口径不一致，量出的分数是 0.87~0.91
> 的无量纲尺度；实际上映射后的分数只有 0.01~0.02。现在探针已补上 token_mapping，
> 并内置了与真实推理函数 `compute_fused_map` 的交叉验证
> （最大偏差 5.2e-04，来源是插值往返误差），此后数字可信。

`probe_m7_scores.py`：用 `m4m6/transistor` 权重、6 张缺陷图，按推理口径
（每张图用**自身原型集**自参照、两侧都过 `token_mapping`）实测：

| 统计量 | 正常像素 | 异常像素 |
|---|---|---|
| p05 | — | 0.010 |
| p25 / p50 / p75 / p95 / p99 | 0.0100 / **0.012** / 0.0125 / **0.016** / 0.021 | 0.010 / **0.016** / 0.019 / 0.023 / — |
| 天然分差(异常 p50 − 正常 p95) | | **−0.001** |

**结论**：正常与异常像素的分数分布**几乎完全重叠**，而且整套分数被压在一个 0.01 量级的窄带里。
只要损失是"图内"的（M5 的 BCE、分割头、cos/MSE），这种跨图重叠就无法被直接约束，
于是 P-AUROC 卡在 +0.5% 一档。这正是引入 **M7（跨图成对 hinge）**的理由。

**尺度标定（决定 M7 的超参）**：固定 margin 在这个尺度下会失效——实测
`margin ≥ 0.010`（>0.4 倍 tau）时 **100% 的困难样本对都被激活**，损失退化成"常数 + 线性推力"。
故 M7 改为**尺度无关**形式：分差先除以 tau = IQR(正常分数)=**0.00249**（detach），margin 以 tau 为单位。

| 归一化 margin | 0.10 | **0.25** | 0.50 | 1.00 |
|---|---|---|---|---|
| L_M7 | 1.549 | **1.658** | 1.849 | 2.260 |
| 激活对比例 | 71.7% | **74.3%** | 78.5% | 85.7% |

据此定 **margin = 0.25 tau、w_rank = 0.02**：使 M7 在训练首轮约占总损失的 **10%**
（0.02×1.66≈0.033，而当时总损失约 0.23~0.30），既不喧宾夺主、也不至于弱到没有梯度。
该取值先经 `probe_m7_scores.py` 定量标定后才写入 `q_m7_train.sh`，不是拍脑袋。

## §25 【重大发现】最终打分图存在 5~12 倍尺度失衡 —— 模型级改进被融合稀释

### 25.1 实测（`probe_map_scales.py`，m4m6/transistor，3 张图 × 尺度 {1.0, 1.5}）
最终评估用的是 `evaluation_batch_fuse`：`fused = 0.5·m_learn + 0.5·m_bank`，其中
* `m_learn` = `1 - max_k cos(token_mapping(patch), token_mapping(proto))` ← **我们所有模型级改动作用的对象**
* `m_bank` = `1 - max_j cos(raw_patch, raw_bank_j)` ← 4 张 shot 的原始特征库，**训练完全不碰**

| 分量 | 均值 | 标准差 |
|---|---|---|
| m_learn（可学习原型图） | **0.0129** | 0.0026 |
| m_bank（原始特征库图） | **0.0703** | 0.0307 |
| 比值 | **5.4×** | **11.8×** |

### 25.2 含义
"0.5 / 0.5" 只是**名义权重**。按幅度算，可学习图的**实际**权重只有
`0.0129/(0.0129+0.0703) ≈ 15.5%`；按**变化量**（真正决定排序的部分）算只有约 `1/(1+11.8) ≈ 8%`。
也就是说：M1/M3/M4/M5/M6/M7 辛苦改进的那个分量，在最终打分里只贡献了不到一成的影响力
——这正好解释了为什么 6 项指标能到 +2~5%，而 P-AUROC 却始终动不了。

**这不是"改动无效"，而是"改动被融合稀释"**。基线（`results/control35/maponly` 的 15 类权重）用的是
**完全相同的打分协议**，所以既有的 +2.5%~+2.9%（5 类、7 指标平均）对比依然公平；
但同时也说明这里有一块**尚未被使用的改进空间**。

## §26 【正确性核查 + 新机制 M8】两套代码副本的权重键不兼容 / w_learn 扫描真相

### 26.1 必须先说清的一个坑：旧权重只能用 `code_norm` 评估
* 基线（`results/control35/maponly/*`）的映射键是 **`token_mapping.0/1/3.*`**（`nn.Sequential` 版）；
* vpt4 的映射键是 **`token_mapping.ln.* / token_mapping.f.*`**（`TokenMapping` 版）。

两者**不通用**：用 vpt4 脚本评估旧权重时，`load_state_dict(..., strict=False)` 会**静默丢掉全部映射权重**
（映射退化成随机初始化），算出来的数字没有意义——我第一次跑基线 w 扫描就踩了这个坑（得到 I-AUROC 0.87
这种"看起来更好"的假结果）。已改用 `--script code_norm/main-fewshot-norm.py` 重跑，并**逐位复现**了
官方基线数字（transistor, w=0.5 → `0.7462/0.7001/0.6909/0.8841/0.3962/0.4614`，与 `all15_g35.csv` 第二行组完全一致）。

**由此同时确认了另外两件事**：
1. 我们的评估管线与记录在案的官方口径**逐位一致**（数值可复现，不是"约等于"）；
2. 两套代码的打分函数**语义等价**：`code_norm` 用 `LayerFusion(mode='sum')`，其实现就是
   `torch.sum(torch.stack(sel,0),0)`，与 `code_vpt4` 里内联的逐层求和完全相同（已做源码级比对：
   `_map28`、`compute_fused_map`、`evaluation_batch_fuse` 的公式逐行一致，差异只有排版与文档字符串）。
   ⇒ **基线与 vpt4 变体的对比是公平的**。

3. **但可学习图仍然打不过原始特征库图**（w=0 那一侧更强）。这就是下一个要攻的点，

   （w=0.3 时基线在 I-AUROC 上会反超，但那是"换协议"，两边必须一起换才算数）。

### 26.3 新机制 M8：把"学到的度量空间"变成 PatchCore 式的原型库
**动机**：可学习图只有 96 个"图像自适应"原型，而原始特征库有 3136 个**真实正常 patch**——
后者覆盖面大得多，所以更强。既然如此，就把**库也映射到同一个学到的度量空间**里，兼得两者：

```
Q = normalize( token_mapping( 可学习原型 ) )  ⊕  normalize( token_mapping( 原始特征库 patch ) )
每图打分 s = 1 - max_Q cos( token_mapping(patch), Q )
```

* 只在 mapping 分支内部改动：**没有启用 MemoryBank 分支**，`--fuse_bank -1` 的语义不变；
* 默认关闭（`--ms_bank_proto 0`），零影响既有实验；
* 评估侧先验证（映射已冻结也能测）：已排队 `tag=vpt4m6bp`（5 类）；
* 若评估侧验证有效，再把它接进**训练**（M5/M7 的原型集也并入映射后的库），让它可被像素级损失训练
  —— 那才是完整的 M8。

## §31 【排错】找到一处真实的"管线不对齐"：原型初始化算子消耗的随机数不同

### 31.1 现象
为判断"leather/pill/zipper 的回退是不是我们机制造成的"，我做了**控制实验 `regD`**
（把所有机制都关掉：`--token_init_std 1e-6 --global_proto 0 --w_div 0 --w_pixel 0 --metric_head 0`，
即尽量复现原始配方），结果：

| 类 / 指标 | 记录基线（可复现） | regD（机制全关，我们的管线） |
|---|---|---|
| pill P-AP | **0.5987**（我用 code_norm 独立重跑得到 0.5987，与记录 0.5986 一致 ✔） | 0.5423（−0.056） |
| zipper P-AP | 0.6963 | 0.6807 |

**连机制全关都对不上**，说明问题不在机制，而在**管线本身**。

### 31.2 定位：初始化算子不同 → 随机流错开 → 训练用的增强序列完全不同
用同一随机种子分别构造两套模型并逐步比对：
* **映射层参数（8 个）逐位完全相同** ✔；
* **可学习原型的初值不同** ✘（都是 ~1e-6 量级，但数值不一样）。

原因：原实现是 `nn.init.normal_(param, std=1e-6)`；我们在 M1 里换成了 `trunc_normal_(param, std=init_std)`。
`trunc_normal_` 内部走的是"均匀分布 → `erfinv`"的变换，**消耗的随机数个数/方式与 `normal_` 不同**，
于是此后所有随机增强（4 张 shot × 22 倍增强）全部错位——
两次训练用的是**两套不同的增强样本序列**，模型当然不会重合
（实测两者训练后的原型余弦只有 0.30，映射权重却只差 2e-4：典型的"同一配方、不同随机流"）。

### 31.3 影响与修法
* **影响**：不仅是"无法逐位复现基线"，更意味着我们此前把"随机流差异"也算进了"机制的效果"里，
  pill/zipper 这类回退很可能被这个因素放大了；
* **修法**（待当前训练跑完后合并，避免同一配置混用两版代码）：
  把 M1 的初始化改回**与原实现同一个算子** `nn.init.normal_(param, std=init_std)`。
  对 M1 本意（std=0.02）几乎没有区别（只在 ±2σ 外做截断，而正态在 ±2σ 外的概率约 5%，
  对"打散原型"的目的一样成立），但能让训练走**与原实现一致的随机流**，
  从而"机制全关 = 复现基线"，A/B 才真正干净。

## §37 【工程修复】统一两个分支的数据源（shot 抽样单一来源 + 落盘 + 防呆）

### 37.1 问题
此前 **训练 / mapping 分支的特征库 / bank 分支** 三处各自写了一遍
`random.seed(seed) + random.sample(sorted(train/good), K)`：
当前结果虽一致，但一致性来自"同种子 + 同排序 + 同随机实现"的**约定**，代码上无任何保证；
一旦把 shot 数改成 8/16，或任一处换了实现，就可能出现"两个分支用了不同正常图"而无人察觉。

### 37.2 改动（只做这一件事）
新增 **`shot_utils.py`**：`get_shots(data_path, cls, shots=K, seed=S)`
* 首次调用生成清单并**落盘** `.shots/<cls>_shot{K}_seed{S}.json`（含文件名列表 + 文件列表哈希）；
* 之后所有脚本**读同一份清单** → 即使改了 K/换了库版本也保持一致；
* 附带 `assert_same_shots()`：两边清单不同**直接报错**，不静默继续。

已接入（本项目当前主路径的全部入口）：
| 入口 | 用途 |
|---|---|
| `code_vpt4/main-fewshot-vpt4.py` | 训练（正常图 shot 选择；日志打印 `[shots] cls shotK hash=... picks=[...]`） |
| `eval_offline.py`、`eval_nocrop.py` | 评估时 mapping 侧"原始特征库"的 shot |
| `cache_bank_nocrop.py`、`eval_bank_combo.py`、`cache_maps.py` | bank 分支建库的 shot |
| `produce_both.py` | 单 loader 同时产出两分支（一次遍历） |

### 37.3 附带发现并加护栏的一类风险：**两份代码副本同名包相互覆盖**
`produce_both.py` 需要同时用到 `code_vpt4`（mapping 模型）与 `code_vpt2`（`augmentation`/`MemoryBank`），
而两份副本里都有 `dinov2` 包名——**先插入 sys.path 的目录优先**，实测 mapping 侧误用了 `code_vpt2/dinov2`，
导致同一权重算出的异常图尺度差了 ~10 倍（mean 0.43 vs 0.043）。
核对结果：`dinov2/models/vision_transformer.py` 两副本**内容不同**，而 `util/memorybank.py`、`util/dataset.py` **完全相同**。
已加两道断言并在构建顺序上隔离：mapping 模型必须在"只有 code_vpt4 在 sys.path 首位"时构建；
`MemoryBank` 实现须与 `code_vpt2` 的副本 **md5 一致**，否则直接报错。

### 37.4 验证（不改变既有结论）
| 验证项 | 结果 |
|---|---|
| 新规范清单 vs 历史实际使用清单（seed=1, shot=4） | **15/15 类完全一致** → 既有结果不受影响 ✔ |
| 换 K 是否仍一致 | K=4/8/16 的清单各自确定且三处共用（transistor: `d0c4c927f728` / `3a95cd21fec8` / `8a516498b293`）✔ |

### 39.2 跑之前发现并修掉的两个真 bug（都属"数据/工程"层，不动模型）
1. **VisA 掩码是 0/1 二值（MVTec 是 0/255）** → 管线 `gt > 0.5` 把异常掩码全判成空 →

2. **4-shot 只加载 35 张合成异常（应 140）** → K 张底图的产物在同一"缺陷类型"目录，
   而 `AnoStylerGeneratedDataset(samples_per_anomaly_type=35)` 每类型只采 35 张 → 监督量退化。
   修法：每底图一个类型目录 `src<stem>` → 每轮 K×35 张（4-shot: 8 iter/epoch）。

| I-AP | 86.10 | 84.47 | 89.17 |
| I-F1 | 85.22 | 84.11 | 86.74 |
